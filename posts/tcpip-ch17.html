第17章 epoll —— 更好的 I/O 复用

发表于2026-07-15|更新于2026-07-16|TCP-IP网络编程
|字数总计:3.4k|阅读时长:14分钟|阅读量:

总结

epoll 是 Linux 下性能最优的 I/O 复用模型，专为克服 select 的三大固有缺陷而设计：用户态↔︎内核态数据拷贝、全量遍历、监视数量限制（FD_SETSIZE/1024）。epoll 的核心思路是将「注册监视对象」与「等待事件」分离——通过 epoll_ctl 注册/修改/删除 fd，通过 epoll_wait 仅获取已就绪的 fd，从 O(n) 降为 O(1)。epoll 支持两种触发模式：条件触发（LT，Level Trigger）和边缘触发（ET，Edge Trigger），ET 模式下必须使用非阻塞 I/O + 循环读写以避免漏读数据。整体而言，epoll 是构建高并发网络服务的基石，也是后续学习 Reactor 模式的前提。

小结::epoll = epoll_create 创建例程 → epoll_ctl（ADD/MOD/DEL）管理监视 → epoll_wait 仅等待就绪 fd。ET 模式通过非阻塞循环读写实现更高效率，是 C10K 问题的经典解。

select 的局限性

为什么还要回顾 select

select 是最早的 I/O 复用函数，跨平台支持好（几乎所有 UNIX 系统都提供），但当并发连接数增大时，select 的性能会急剧下降。理解 select 的问题，才能更好地理解 epoll 的设计动机。

select 的三大缺陷

缺陷 说明
内核态 ↔︎ 用户态数据拷贝 每次调用 select 都需要将 fd_set 从用户空间复制到内核空间，监视数量越大开销越大
全量遍历所有 fd 内核需要遍历所有被监视的 fd 来检查是否有事件发生，时间复杂度 O(n)
监视数量上限 FD_SETSIZE 通常为 1024，超出则行为未定义

除此之外，select 的 fd_set 是事件驱动型（电平触发），每次调用前都必须重新注册所有监视对象，因为内核会修改 fd_set 来通知应用程序（即 readfds 等参数既是输入也是输出）。

epoll 的优势

epoll 的三大设计突破

epoll 将 select 的三个核心缺陷一一化解：

select 的问题 epoll 的解决方案
每次都需要传递 fd_set 到内核 epoll 在内核维护一个事件表（eventpoll），通过 epoll_ctl 一次性注册，后续不再传递
需要遍历所有 fd 寻找就绪事件 epoll_wait 仅返回发生了事件的 fd，无需遍历
FD_SETSIZE 上限（通常 1024） 无上限（仅受系统文件描述符总数限制，cat /proc/sys/fs/file-max 可查看）

性能对比示意图

对于连接数少、低频 I/O 的场景，select 差异不大；但在数千并发连接下，epoll 的 O(1) 特性会带来数量级的性能提升。

epoll 的三个核心函数

epoll_create —— 创建 epoll 例程

  • size：Linux 2.6.8 之后内核动态管理事件表，size 参数已被忽略，但为了可移植性仍需传入 > 0 的值（通常传 10 或 100）。
  • 返回的文件描述符用作 epoll 例程的句柄，后续所有 epoll 操作都需要它。
  • 不再使用时必须 close() 关闭它。

epoll_ctl —— 注册/修改/删除监视对象

op 参数：

操作 宏 含义
注册 EPOLL_CTL_ADD 将 fd 注册到 epoll 例程中
修改 EPOLL_CTL_MOD 修改已注册 fd 的事件类型
删除 EPOLL_CTL_DEL 从 epoll 例程中删除 fd（event 传 NULL）

struct epoll_event 结构体：

常用 events 标志：

宏 含义
EPOLLIN 读事件（数据可读）
EPOLLOUT 写事件（可写入数据）
EPOLLET 设置边缘触发模式（默认是条件触发）
EPOLLRDHUP 对端关闭连接或半关闭（Linux 2.6.17+）
EPOLLHUP 挂起事件
EPOLLERR 错误事件

epoll_wait —— 等待事件发生

  • events：输出参数，内核将就绪的事件填充到此数组中。
  • maxevents：最多返回的事件数（通常等于 events 数组大小）。
  • timeout：
    • -1：无限阻塞直到有事件发生
    • 0：立即返回（非阻塞轮询）
    • > 0：超时毫秒数

epoll_wait 只返回有事件发生的 fd，这正是 epoll 性能优于 select 的根本原因——无需遍历那些没有活动的 fd。

epoll 的整体流程

条件触发（LT） vs 边缘触发（ET）

条件触发（Level Trigger）

LT 是 epoll 的默认工作模式，行为与 select 类似：只要 fd 上有数据未读完，epoll_wait 就会反复通知该事件。

边缘触发（Edge Trigger）

ET 只在状态变化时通知一次，即从「无数据」变为「有数据」的瞬间触发一次，之后即使还有数据未读也不再通知。

ET 的实现要点

使用 ET 模式必须满足两个条件：

  1. 将文件描述符设置为非阻塞模式
  2. 配合循环读写，每次 read/write 直到返回 EAGAIN

LT vs ET 对比

对比维度 LT（条件触发） ET（边缘触发）
通知方式 只要有数据就反复通知 仅状态变化时通知一次
编程复杂度 低，按需读取即可 高，需非阻塞循环读取
效率 可能产生多余通知 通知次数最少，效率更高
适用场景 通用场景、简单服务器 高并发、高性能服务器
阻塞/非阻塞 均可 必须非阻塞模式

为什么 ET 必须使用非阻塞 I/O

ET 模式下事件只通知一次，所以必须一次性把数据全部读完。如果用阻塞 I/O，若在循环的最后一次 read 时无数据可读，线程会阻塞在 read 调用上，导致整个进程卡死。

总结与思考

epoll 的适用场景

  • 高并发连接（数千到数万连接）：epoll 是 Linux 上的最优选择
  • 长连接场景（如 WebSocket、即时通讯）
  • 需要边缘触发减少不必要的系统调用

不适用场景

  • 连接数极少（几十个以下）：select/poll 更简单，差别不大
  • 跨平台需求：select 更通用（macOS 使用 kqueue，Windows 使用 IOCP）

关键点自测

  1. 为什么 epoll 不需要像 select 那样每次传递监视对象？
  2. EPOLL_CTL_DEL 时 event 参数应该传什么？
  3. 为什么 ET 模式必须配合非阻塞 I/O？
  4. 如何判断非阻塞读取时数据已经全部读完？
  5. 如果 epoll 用 LT 模式，BUF_SIZE 设很小会发生什么？
  6. epoll_wait 的返回值有什么意义？

答案：① 内核维护了事件表；② NULL；③ 阻塞读最后一次会永远阻塞；④ 返回 -1 且 errno == EAGAIN；⑤ 会多次通知，每次只读少量字节——这是 LT 模式的特点，效率下降但不会丢失数据；⑥ 返回就绪事件的数量，即 events 数组中有效元素的个数。
