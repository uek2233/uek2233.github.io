总结

小结:: 本章解决第 4 章遗留的「回声客户端可能收不完数据」的问题，引出应用层协议的设计思想：TCP 没有数据边界，必须由应用层自己约定消息格式。最后通过「计算器」示例，演示如何用自定义协议实现一次完整的 TCP 通信。

  1. 回声客户端问题：一次 read 可能收不完服务器回显的所有数据
  2. 完美实现：循环调用 read，直到收满为止
  3. 关键点：客户端必须知道该收多少字节——这就是应用层协议要解决的问题
  4. 应用层协议：约定「先传长度，再传数据」的报文格式
  5. 计算器示例：客户端发送「操作数个数 + 操作数 + 运算符」，服务器计算后返回结果

回声客户端的完美实现

问题回顾

第 4 章的回声客户端只调用了一次 read：

由于 TCP 没有数据边界，服务器回显的字符串可能被拆成多个包到达，一次 read 往往收不完。

解决方案：循环接收

思路：循环调用 read，直到收到的总字节数等于发送的字节数。

💡 这里的核心思想是：发送方告诉接收方「这次一共发多少字节」，接收方就循环读到这么多字节为止。这个「告诉对方长度」的约定，就是最简单的应用层协议。

完整代码：echo_client2.c

⚠️ 为什么可以确定收满？ 因为回声服务器的行为是「收到多少就回显多少」，客户端发送 str_len 字节，服务器就会回显 str_len 字节。客户端只要循环收到 str_len 字节即可。但如果服务器返回的数据量不确定呢？——那就需要更完善的应用层协议了。

应用层协议的设计

为什么需要应用层协议？

TCP 是字节流协议，没有数据边界。read 函数不知道「一条消息」在哪里结束：

  • 可能一次 read 只读到半条消息
  • 也可能一次 read 读到了两条消息

因此，应用程序必须自己约定消息的格式，让接收方能够判断一条消息何时结束，这种约定就是应用层协议。

常见设计思路

方案 思路 特点
固定长度 每条消息固定 N 字节，收满 N 字节即一条消息 简单，但浪费空间
特殊分隔符 用 \n 等特殊字符标记消息结束（如 HTTP 头） 简单，但数据本身不能包含分隔符
长度前缀 先发送 4 字节的消息长度，再发送消息内容 最常用，灵活高效

📌 本章计算器示例采用的就是长度前缀 + 固定字段的混合方案：先发操作数个数（1 字节），再发各操作数（每个 4 字节）和运算符（1 字节）。

本章总结 🎯

核心概念 说明
回声客户端问题 TCP 无数据边界，一次 read 可能收不完数据
完美实现 循环 read，收满发送的字节数为止
应用层协议 应用自己约定消息格式（定长 / 分隔符 / 长度前缀）
计算器协议 个数(1B) + 操作数(N×4B) + 运算符(1B)，结果固定 4B
关键思想 发送方告诉接收方「发多少」，接收方「收到够为止」

一句话总结：TCP 只管字节流，不管消息边界——应用层协议就是双方约定「一条消息长什么样、什么时候结束」的规则，它是所有网络应用设计的基石。
