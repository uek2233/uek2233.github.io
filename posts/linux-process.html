进程与程序

进程其实就是一个可执行程序的实例。程序（Program）是静态的、存放在磁盘上的可执行文件；进程（Process）是程序被加载到内存中运行后的动态实体，是操作系统进行资源分配的基本单位。

程序是如何被执行起来的

  1. 链接器：main() 函数之前需要先执行一段引导代码（启动例程，由 crt1.o / crti.o 等目标文件提供），最终由这段引导代码去调用应用程序的 main() 函数。编写应用程序时不用考虑引导代码的问题——在编译链接时，由链接器将引导代码链接到应用程序当中，一起构成最终的可执行文件
  2. 加载器：程序运行需要通过操作系统的加载器（loader）来实现。加载器是操作系统中的程序：当执行一个程序时，加载器负责将此应用程序加载到内存中去执行
  3. argc 和 argv 传参：命令行参数由 shell 进程逐一解析，shell 进程会将这些参数传递给加载器；加载器加载应用程序时会将其传递给应用程序的引导代码；当引导代码调用 main() 函数时，再由它最终传递给 main() 函数

程序的结束

进程终止的方式：

  • main() 中执行 return（等价于调用 exit()，返回值即退出状态）
  • 调用 exit()
  • 调用 abort()（异常终止，产生 SIGABRT，详见 信号）
  • 进程接收到一个信号，如 SIGKILL（被 kill -9 杀死）、SIGSEGV（段错误）等

atexit() 库函数用于注册一个进程在正常终止时要调用的函数（如清理资源、落盘日志）。

进程号

系统通过进程号（Process ID, PID）唯一标识系统中的某一个进程。每个进程还有一个父进程号（PPID），指向创建它的父进程。

进程的环境变量

每一个进程都有一组与其相关的环境变量。这些环境变量以字符串形式存储在一个字符串数组列表中，把这个数组称为环境列表（environment list）。其中每个字符串都是以 名称=值（name=value）形式定义，每一个环境变量都有它所表示的含义（如 PATH 表示命令搜索路径、HOME 表示用户主目录）。

进程的环境变量是从其父进程中继承过来的：在 shell 终端下执行一个应用程序，该进程的环境变量就是从其父进程（shell 进程）中继承的。所以修改 shell 的 export，会影响之后启动的所有子进程。

进程的内存布局与虚拟地址空间

进程的内存布局

一个进程在用户空间中的内存，从高地址到低地址可划分为以下几个核心区域：

  1. 环境变量与命令行参数
    • 位置：用户空间的最高地址端
    • 内容：存放程序启动时传入的命令行参数（如 argv）和系统环境变量（如 PATH、HOME）
  2. 栈区（Stack）
    • 位置：由高地址向低地址增长
    • 内容：存放函数的局部变量、函数参数值以及函数调用的上下文（返回地址等）
    • 特点：由编译器自动分配和释放，空间连续且容量有限（Linux 下可用 ulimit -s 查看，默认通常为 8MB）
  3. 文件映射与匿名映射区（Memory Mapping Segment）
    • 位置：位于栈和堆之间
    • 内容：主要用于动态链接库（.so 文件）的加载、共享内存映射，以及使用 mmap 系统调用申请的大块内存（malloc 申请超过 128KB 的大块内存时，glibc 底层也是用 mmap 实现）
  4. 堆区（Heap）
    • 位置：由低地址向高地址增长，与栈区相对扩展
    • 内容：存放程序运行期间动态分配的内存（如 C 语言的 malloc 或 C++ 的 new）
    • 特点：由程序员手动申请和释放，若不释放易造成内存泄漏；空间不连续，容量几乎取决于系统的虚拟内存大小
  5. BSS 段（Block Started by Symbol）
    • 位置：位于堆区下方、数据段上方
    • 内容：存放未初始化或初始化为 0 的全局变量和静态（static）变量
    • 特点：在可执行文件中不占用实际磁盘空间，只记录大小，程序加载时由内核统一清零
  6. 数据段（Data Segment）
    • 位置：位于 BSS 段下方
    • 内容：存放已初始化且不为 0 的全局变量和静态变量
    • 特点：属于静态内存分配，其寿命贯穿整个程序运行期
  7. 代码段与常量区（Text & Read-Only Data）
    • 位置：用户空间的最低地址端
    • 内容：
      • .text（代码区）：存放 CPU 执行的机器指令（二进制代码）
      • .rodata（只读数据区）：存放只读常量，例如字符串字面量 "hello world"
    • 特点：通常是只读的，防止程序意外修改自身指令

虚拟地址空间

在 Linux 系统中，每一个进程都在自己独立的地址空间中运行。在 32 位系统中，每个进程的逻辑地址空间均为 4GB，这 4GB 的内存空间按照 3:1 的比例进行分配：用户进程享有 3G 的空间（0x00000000 ~ 0xBFFFFFFF），内核独自享有剩下的 1G 空间（0xC0000000 ~ 0xFFFFFFFF）。

💡 注意：4GB 是虚拟地址空间，不是物理内存。进程的虚拟地址会通过硬件 MMU（内存管理单元，Memory Management Unit） 映射到实际的物理地址空间中：建立虚拟地址到物理地址的映射关系后，对虚拟地址的读写操作实际上就是对物理地址的读写操作（"翻译"由 MMU 硬件完成）。64 位系统下地址空间更大（x86-64 用户空间约 128TiB），不再受 3:1 的限制。

为什么要使用虚拟地址

不使用虚拟地址（程序直接访问物理内存）的缺点：

  1. 内存使用效率低：应用程序必须加载到内存中才能运行。当多个程序需要运行时，必须保证这些程序用到的内存总量小于计算机实际物理内存的大小；当内存空间不足时，就需要把其它程序暂时拷贝到硬盘中（swap），然后将新程序装入内存。大量数据装入装出，内存的使用效率非常低
  2. 进程地址空间不隔离：由于程序直接访问物理内存，每一个进程都可以修改其它进程的内存数据，甚至修改内核地址空间中的数据——恶意程序可以随意修改别的进程，造成破坏，系统不安全、不稳定
  3. 无法确定程序的链接地址：链接地址和运行地址必须一致，否则程序无法运行！因为程序代码加载到内存的地址是由系统随机分配的、无法预知，所以程序的运行地址在编译程序时无法确认

使用虚拟地址的优点：

  1. 进程与进程、进程与内核相互隔离：每个进程都以为自己独占整个地址空间，互不干扰
  2. 每个进程都有自己的映射表，可以让不同进程的虚拟地址空间映射到相同的物理地址空间中——通常，共享内存（shared memory）就是利用这一点实现进程间通信（见 IPC 相关笔记）
  3. 便于实现内存保护机制：多个进程共享内存时，允许每个进程对内存采取不同的保护措施。例如，一个进程可以以只读方式访问内存，而另一进程则能够以可读可写的方式访问
  4. 编译应用程序时，无需关心链接地址：现代编译器默认生成位置无关/固定虚拟地址布局的可执行文件，运行地址由内核加载时决定，程序内部的链接地址由虚拟地址空间保证一致

fork() — 创建子进程

作用:: 创建一个子进程。调用完成后系统中将存在两个进程：一个是原进程（父进程），另一个是创建出来的子进程，并且每个进程都会从 fork() 函数的返回处继续执行。

用法：

返回值（fork() 调用一次，返回两次，这是它最特殊的点）：

  • 父进程中：返回子进程的 PID（> 0）
  • 子进程中：返回 0
  • 调用失败：父进程返回 -1，不创建子进程，并设置 errno

fork 之后进程的状态：

  • 子进程是父进程的一个副本：子进程拷贝了父进程的数据段、堆、栈，以及继承了父进程打开的文件描述符
  • 父进程与子进程并不共享这些存储空间——这是子进程对父进程相应部分存储空间的完全复制（现代 Linux 用写时复制 COW 优化，见文末补充，效果上等价但效率高得多）。执行 fork() 之后，每个进程均可修改各自的栈数据以及堆段中的变量，而并不影响另一个进程
  • 对于程序代码段（文本段）：两个进程执行相同的代码段，因为代码段是只读的，也就是说父子进程共享代码段，内存中只存在一份代码段数据
  • 子进程被创建出来之后便是一个独立的进程：拥有自己独立的进程空间、系统内唯一的进程号、自己独立的 PCB（进程控制块），会被内核同等调度执行，参与到系统的进程调度中

注意事项：

  • C 库函数 exit() 建立在系统调用 _exit() 之上。在调用了 fork() 之后，父、子进程中一般只有一个会通过 exit() 退出进程，而另一个则应使用 _exit() 退出（推荐：子进程 _exit()，父进程 exit()，原因见"进程的诞生与终止"）
  • 调用 fork() 之后，无法确定父、子两个进程谁将率先访问 CPU——这就是 fork 之后的竞争条件。如果程序逻辑依赖执行顺序，必须用同步机制（信号/管道等）显式同步，参考 Processe/src/fork3.cc（子进程 sleep 后发 SIGUSR1，父进程 sigsuspend 挂起等待）

fork() 函数的两个典型使用场景：

  1. 父进程希望子进程复制自己，使父进程和子进程同时执行不同的代码段：典型如网络服务器——父进程等待客户端的服务请求，接收到客户端请求事件后调用 fork() 创建子进程，让子进程去处理此请求，父进程则继续等待下一个服务请求
  2. 一个进程要执行不同的程序：在程序 app1 中调用 fork() 创建子进程，子进程再去执行另一个程序 app2（通过 exec 族，见第七章），子进程将从 app2 程序的 main() 函数开始运行

父、子进程间的文件共享

fork() 之后，父、子进程对应的文件描述符均指向相同的文件表（内核的 open file description），也就意味着它们指向了磁盘中相同的文件，因而这些文件在父、子进程间实现了共享——最典型的体现是：文件偏移量是共享的。如果子进程更新了文件偏移量，那么这个改变也会影响到父进程中相应文件描述符的位置偏移量。

作用:: 与 fork() 类似的子进程创建函数，但效率更高，是为"子进程立即执行 exec() 新程序"这个场景专门设计的（即 fork() 的第二个使用场景）。

  1. vfork() 并不会将父进程的地址空间完全复制到子进程中——因为子进程会立即调用 exec()（或 _exit()），于是也就不会引用该地址空间的数据。不过在子进程调用 exec() 或 _exit() 之前，它在父进程的空间中运行，子进程共享父进程的内存
  2. vfork() 保证子进程先运行，子进程调用 exec() 之后父进程才可能被调度运行

注意事项：

  • 虽然 vfork() 在效率上优于 fork()，但它可能会导致一些难以察觉的程序 bug（子进程共享父进程内存，若在 exec 前修改了变量/返回父进程栈，行为诡异），所以尽量避免使用 vfork() 创建子进程
  • 现代 Linux 的 fork() 已用写时复制（COW）实现，绝大多数场景直接用 fork() 即可，不必再纠结 vfork 的性能优势

进程的诞生与终止

Linux 系统下的所有进程都是由其父进程创建而来的：在 shell 终端通过命令方式执行 ./app，app 进程就是由 shell 终端进程创建出来的，shell 终端就是该进程的父进程。

进程号为 1 的进程便是所有进程的父进程，通常称为 init 进程（现代系统多为 systemd，仍占 PID 1）。它是 Linux 系统启动之后运行的第一个进程，管理着系统上所有其它进程。init 进程由内核启动，PID 总是为 1，它是所有孤儿进程的"养父"——一切从 1 开始、一切从 init 进程开始。

终止状态（termination status）

exit() 函数的 status 参数定义了进程的终止状态，父进程可以调用 wait() 函数获取该状态。虽然参数 status 定义为 int 类型，但仅有低 8 位表示它的终止状态（所以退出码范围是 0~255，exit(-1) 实际得到 255）。

一般来说，终止状态为 0 表示进程成功终止，而非 0 值则表示进程在执行过程中出现了一些错误而终止（惯例：0 成功、非 0 出错）。

exit() 内部到底做了什么

exit() 函数会执行的动作如下：

  1. 如果程序中注册了进程终止处理函数（atexit()），会逆序调用这些终止处理函数
  2. 刷新 stdio 流缓冲区（把缓冲中的数据真正写出去）
  3. 执行 _exit() 系统调用，真正退出

为什么 fork 之后父、子进程不能用同一个 exit()

父、子进程不应都使用 exit() 终止，只能有一个进程使用 exit()、另一个使用 _exit()（一般推荐：子进程 _exit()、父进程 exit()）。

原因在于 stdio 缓冲区：fork() 之后创建的子进程也自然拷贝了父进程的 stdio 缓冲区数据。若父子都调用 exit()，两者都会各自刷新自己那份缓冲区——例如父进程之前在缓冲区里写了一个字符串还没 flush，fork 后父子各有一份，调用 exit() 时两边都把同一份字符串打印一遍，于是就会看到打印出了两次相同的字符串。

参考 Processe/src/fork1.cc：父进程 exit(0)、子进程 _exit(0)——子进程不刷新自己拷贝来的缓冲区，避免了重复输出。

💡 容器里的真实坑：如果容器的 PID 1 进程不是真正的 init/systemd（比如用 sleep infinity 之类的命令占着 PID 1），它不会调用 wait() 回收子进程。被它收养的孤儿进程一旦退出就会变成永远清不掉的僵尸进程（见下一章 zombie 演示和文末补充）。生产容器建议用 tini / dumb-init 之类带回收能力的进程当 PID 1。

监视子进程

为什么要 wait()

父进程创建子进程后，需要知道子进程的终止情况并回收它的资源：

  • wait() 可以获取子进程的终止状态（正常退出码 / 被哪个信号杀死等）
  • 更重要的是回收子进程的资源——子进程终止后如果没有父进程调用 wait 收尸，会残留为僵尸进程（见下文），占用内核进程表项。俗称为子进程"收尸"

wait() — 等待任意子进程终止

作用:: 阻塞等待任意一个子进程终止，获取其终止状态并回收资源。若成功则返回终止的子进程对应的进程号；失败则返回 -1。

用法：

参数：status：输出参数，保存子进程的终止状态（可为 NULL，表示不关心状态，只收尸）

返回值：成功返回终止子进程的 PID；失败返回 -1（并设置 errno）

wait() 的三种行为：

  1. 如果其所有子进程都还在运行，wait() 会一直阻塞等待，直到某一个子进程终止
  2. 如果调用 wait() 的进程并没有子进程（没有需要等待的子进程），wait() 将返回错误 -1，并将 errno 设置为 ECHILD
  3. 如果在调用 wait() 之前，它的子进程当中已经有一个或多个终止了（已处于僵尸状态），那么调用 wait() 不会阻塞，立即回收并返回

注意事项：

  • wait(&status) 与 waitpid(-1, &status, 0) 等价
  • 若父进程有多个子进程，wait() 回收的是任意一个（不指定具体 PID），返回值告诉你回收的是谁

僵尸进程与孤儿进程

1. 孤儿进程（父进程先于子进程结束）： 父进程先于子进程结束，意味着此时子进程变成了一个"孤儿"，这种进程称为孤儿进程。所有的孤儿进程都自动成为 init 进程（PID 1）的子进程——某一子进程的父进程结束后，该子进程调用 getppid() 将返回 1，init 进程变成了孤儿进程的"养父"。这也是判定某一子进程的"生父"是否还"在世"的方法之一。

2. 僵尸进程（子进程先于父进程结束，父进程没来得及收尸）： 子进程先于父进程结束，此时父进程还未来得及给子进程"收尸"，那么子进程就变成了一个僵尸进程（Zombie）。僵尸进程已经终止、不占 CPU，但仍保留着内核进程表项（PCB 残留），等待父进程读取退出状态。当父进程调用 wait()（或其变体）为子进程"收尸"后，僵尸进程就会被内核彻底删除。

  • 如果父进程没有调用 wait() 就退出了，此时 init 进程将会接管它的子进程并自动调用 wait()，从而从系统中移除僵尸进程（前提是 init 真的会 wait——见容器 PID 1 的坑）
  • 如果系统中存在大量的僵尸进程，它们势必会填满内核进程表，从而阻碍新进程的创建。所以在程序设计中，一定要监视子进程的状态变化：如果子进程终止了，要调用 wait() 将其回收，避免僵尸进程
  • 已经产生的僵尸进程无法直接"杀死"（它已经死了），只能等其父进程终止、或杀死其父进程，让 init 进程来处理；杀死父进程之后，僵尸进程也会随之被清理

SIGCHLD 信号与"漏网之鱼"问题

子进程终止时，内核会向父进程发送 SIGCHLD 信号（默认动作是忽略）。父进程可以在 SIGCHLD 处理函数中调用 wait() 回收子进程，实现"子进程一死就自动收尸"。

但这里有个经典陷阱：当调用信号处理函数时，内核会暂时将引发调用的信号添加到进程的信号掩码中（除非 sigaction() 指定了 SA_NODEFER）。这样一来，当 SIGCHLD 信号处理函数正在为一个终止的子进程"收尸"时，如果相继有两个子进程终止，即使产生了两次 SIGCHLD 信号，父进程也只能捕获到一次。结果是父进程的 SIGCHLD 处理函数每次只调用一次 wait()，就会导致有些僵尸进程成为"漏网之鱼"。

解决方案：在 SIGCHLD 信号处理函数中循环以非阻塞方式调用 waitpid(-1, ..., WNOHANG)，直至再无其它终止的子进程需要处理为止：

执行新程序

execve() — 执行新程序的系统调用

作用:: 加载并执行一个全新的程序。它会用新程序的代码、数据、堆栈等完全替换当前进程的内容，但进程的 PID（进程ID）保持不变——进程还是那个进程，只是"芯"被换掉了。exec 成功后不会返回（成功即"一去不回"），只有失败才返回 -1。

用法：

参数：

  • filename：要执行的目标程序的文件路径（可以是二进制可执行文件，也可以是带解释器的脚本）
  • argv：传给新程序的命令行参数数组，以 NULL 结尾（其中 argv[0] 通常是程序自身的名称）
  • envp：传给新程序的环境变量数组，同样以 NULL 结尾

注意事项：

  • exec 不创建新进程——PID 不变，进程的其它属性（打开的文件描述符中未设 FD_CLOEXEC 的、进程号、父进程号等）大部分保留
  • 成功不返回：exec 之后的代码永远不会执行（除非 exec 失败）
  • 从 shell 角度看，fork() + exec() 的组合就是"运行一个新程序"的标准姿势：fork 出子进程，子进程 exec 替换成新程序，父进程 wait 回收

实现原理：system() 内部通过调用 fork()、execl() 以及 waitpid() 三个函数实现：首先 fork() 创建一个子进程来运行 shell（可以把这个子进程称为 shell 进程），并通过 shell 执行参数 command 所指定的命令。

注意事项：

  • 效率低：system() 运行 shell 命令需要至少创建两个进程——一个进程用于运行 shell、另外一个或多个进程则用于运行 command 中解析出来的命令（每一个命令都会调用一次 exec 函数执行）。所以使用 system() 效率会大打折扣，高频路径不要用
  • 安全（命令注入）：command 会交给 shell 解析，如果命令字符串中拼接了外部输入（如用户数据、文件名），可能被注入额外的 shell 命令——处理不可信输入时不要用 system()，优先考虑 exec 族直接执行程序
  • command 为 NULL 时，system() 仅检测 shell 是否可用（可用返回非 0）
  • 返回值是 waitpid 得到的编码后状态，需要用 WIFEXITED/WEXITSTATUS 等宏解析；它无法区分"命令正常退出"与"shell 启动失败"

进程关系

进程之间的关系从简单到复杂分为三种：无关系、父子进程关系、进程组与会话。

进程组（Process Group）：设计进程组实质上是为了方便对进程进行管理。假设为了完成一个任务需要并发运行 100 个进程，当处于某种场景需要终止这 100 个进程时，若没有进程组就需要一个一个去终止，非常麻烦且容易出现一些问题；有了进程组的概念之后，就可以将这 100 个进程设置为一个进程组，这些进程共享一个进程组 ID（PGID），终止这 100 个进程只需要终止该进程组（kill -PID 或 kill -- -PGID）。

进程组的基本规则：

  1. 每个进程必定属于某一个进程组、且只能属于一个进程组
  2. 每一个进程组有一个组长进程，组长进程的 ID 就等于进程组 ID
  3. 在组长进程的 ID 前面加上一个负号即是操作进程组（如 kill -TERM -PGID）
  4. 组长进程不能再创建新的进程组
  5. 只要进程组中还存在一个进程，则该进程组就存在——这与其组长进程是否终止无关
  6. 一个进程组可以包含一个或多个进程；进程组的生命周期从被创建开始，到其内所有进程终止或离开该进程组
  7. 默认情况下，新创建的进程会继承父进程的进程组 ID

会话（Session）：会话是一个或多个进程组的集合。一个会话可包含一个或多个进程组，但只能有一个前台进程组，其它的是后台进程组；每个会话都有一个会话首领（session leader），即创建会话的进程。一个会话可以有控制终端、也可没有控制终端；在有控制终端的情况下也只能连接一个控制终端（通常是登录到其上的终端设备）。

  • 会话的首领进程连接一个终端之后，该终端就成为会话的控制终端；与控制终端建立连接的会话首领进程被称为控制进程
  • 将产生在终端上的输入和信号将发送给会话的前台进程组中的所有进程（所以只有前台进程组能收到 Ctrl+C）
  • 会话的首领进程的进程组 ID 将作为该会话的标识，也就是会话 ID（sid）；默认情况下，新创建的进程会继承父进程的会话 ID

守护进程

守护进程（Daemon）是运行在后台的一种特殊进程，它独立于控制终端并且周期性地执行某种任务或等待处理某些事情的发生。

守护进程的特点：

  1. 一般在系统启动时开始运行，除非强行终止，否则直到系统关机都会保持运行
  2. 普通进程与运行它的终端相绑定：当控制终端被关闭时，该会话就会退出，由控制终端运行的所有进程都会被终止。而守护进程能突破这种限制——它脱离终端并且在后台运行
  3. 守护进程通常称为 Daemon，一般进程名后面带 d 就表示它是一个守护进程（sshd、crond、mysqld……）
  4. 守护进程自成进程组、自成会话，即 pid == gid == sid

编写守护进程的标准步骤

以 Processe/src/daemon.cc 为参考，标准流程如下：

① 创建子进程、终止父进程 子进程继承了父进程的进程组 ID，但它有自己独立的进程 ID，这保证了子进程不是一个进程组的组长进程——这是下面调用 setsid() 的先决条件。父进程直接退出（终端上立刻回到 shell 提示符，给人"程序已经启动完了"的反馈）。

② 子进程调用 setsid() 创建新会话 因为子进程不是进程组组长，所以 setsid() 会成功：子进程创建新的会话并成为会话首领进程，同时创建新的进程组并成为组长进程，且新会话没有控制终端。这一步有三个作用：让子进程摆脱原会话的控制、摆脱原进程组的控制、摆脱原控制终端的控制。

③ 将工作目录更改为根目录（或其它固定目录） 让 / 作为守护进程的当前目录（避免占用某个被卸载的挂载点；也可以像 daemon.cc 一样 chdir 到自己的日志目录，保证相对路径日志可写）。

④ 重设文件权限掩码 umask fork() 新建的子进程继承了父进程的文件权限掩码，这可能给子进程创建文件带来麻烦。把文件权限掩码设置为 0，确保子进程有最大操作权限，大大增强守护进程的灵活性。

⑤ 关闭不再需要的文件描述符 子进程继承了父进程的所有文件描述符，这些被打开的文件可能永远不会被守护进程读或写，但它们一样消耗系统资源、可能导致所在文件系统无法卸载，所以必须关闭（daemon.cc 中用循环关闭 0 到 getdtablesize() 的所有 fd）。

⑥ 将文件描述符 0、1、2 定位到 /dev/null 守护进程的标准输入、标准输出、标准错误重定向到 /dev/null——它的输出无处显示，也无处从交互式用户那里接收输入（同时也避免后续 open 时误占 0/1/2 导致 printf 输出跑到奇怪的文件里）。

⑦ 其它可选收尾：忽略 SIGCHLD 信号（signal(SIGCHLD, SIG_IGN)）——让内核将孙进程的僵尸转交给 init 进程处理，既不会产生僵尸进程，又省去了服务器进程回收子进程所占用的时间。

💡 二次 fork 的传统：老教材常写"fork 两次"。其实在 Linux 上，单次 fork 后子进程 PID 必然不等于其 PGID（PGID 是父进程 PID），子进程必然不是组长，setsid() 必然成功，所以一次 fork 就够（daemon.cc 就是单 fork）。二次 fork 是 SVR4 时代的习惯（防止进程日后重新获得控制终端等边缘场景），了解即可。

SIGHUP 信号

作用：当用户准备退出会话时，系统向该会话发出 SIGHUP 信号；会话将 SIGHUP 信号发送给所有子进程，子进程接收到 SIGHUP 信号后便会自动终止；当所有会话中的所有进程都退出时，会话也就终止了。

注意事项：

  • 因为程序当中一般不会对 SIGHUP 信号进行处理，所以对应的处理方式为系统默认方式——SIGHUP 信号的系统默认处理方式便是终止进程（终端关闭时，前台进程组里没做防护的程序就被"挂断"杀掉了）
  • 守护进程通过 setsid() 脱离了控制终端，不在任何会收到 SIGHUP 的会话/终端里，因此终端关闭不影响它——这是守护进程能长期存活的关键
  • 有些守护进程（如 sshd、nginx master）会用 SIGHUP 作为"重载配置"的触发信号（捕获后重新读配置而非退出），这是对默认行为的自定义覆盖

单例模式运行

通常情况下，一个程序可以被多次执行——程序在还没结束的情况下又再次执行，系统中同时存在多个该程序的实例化对象（进程）。当程序只能被执行一次，只要该程序没有结束就无法再次运行，我们把这种情况称为单例模式运行（singleton）。典型场景：守护进程、独占资源的服务（如只允许一个实例操作某硬件设备）。

文件锁方案（flock + pid 文件）

实现单例最稳健的方式是文件锁 + pid 文件：

  1. 程序启动之后，首先打开（必要时创建）锁文件。open 时一般使用 O_WRONLY | O_CREAT（注意不要带 O_TRUNC——若加锁失败，不能把别的实例写入的内容截掉）
  2. 尝试去获取文件锁（flock + LOCK_EX | LOCK_NB 非阻塞互斥锁）。加锁成功：说明没有其它实例在运行，将程序的进程号（PID）写入该文件，然后不要关闭文件或解锁，保证进程一直持有该文件锁
  3. 加锁失败（errno == EWOULDBLOCK）：说明程序已经被运行，本次启动直接退出
  4. 进程退出（无论正常退出还是崩溃）时，内核会自动释放该进程持有的 flock——所以即使程序崩溃，锁也会自动消失，不会出现"锁残留导致永远无法再启动"的问题

  • 传统上还有"只用 pid 文件 + 检查进程是否存在"的做法，但进程崩溃后 pid 文件会残留、PID 可能被复用，不可靠——文件锁方案更稳

补充：进程编程实战要点

fork 与写时复制（Copy-on-Write, COW）

早期 UNIX 的 fork() 确实把父进程的地址空间完整复制一份给子进程，代价高昂。现代 Linux 的 fork 采用写时复制优化：

  • fork 时父子进程共享同一份物理内存页，页表标记为只读
  • 只要双方都只读，就零拷贝、零开销
  • 一旦某一方要写某个页，触发缺页异常，内核才真正复制该页再允许写

所以 fork 的开销与"父进程地址空间大小"无关，只与实际写入的页面数量有关——这也是 fork + exec 组合（子进程几乎不写内存就换程序）非常高效的原因。

进程数量上限

  • 每个用户的进程数上限：ulimit -u 查看（fork 失败 errno = EAGAIN 常与此有关）
  • 系统全局 PID 上限：/proc/sys/kernel/pid_max（默认通常 32768 或 4194304，超出后 PID 回绕复用）
  • 排查"fork 不了新进程"：ps -eLf | wc -l 看进程/线程总数，检查是否被僵尸进程堆满，或触达 ulimit

容器 PID 1 不回收僵尸的坑

容器里 PID 1 如果不是 init/systemd/tini 这类会 wait() 的进程（比如直接 sleep infinity、bash），那么所有被它收养的孤儿进程退出后都无人收尸，会永久变成僵尸（实测：容器里反复启动/杀掉 daemon 后，ps -ef 能看到一串 PPID=1 的 [daemon] <defunct>，怎么 kill 都清不掉，只能重启容器）。

  • 表现：ps -ef | grep defunct 出现 PPID=1 的僵尸
  • 危害：僵尸填满进程表（默认上限 /proc/sys/kernel/pid_max），最终导致无法创建新进程
  • 解法：生产容器把 PID 1 换成 tini / dumb-init（或在 entrypoint 里 exec 真正的 init）；自己写容器内常驻服务时，要么妥善 wait 子进程，要么忽略 SIGCHLD 让内核自动回收

同样是 printf 没 flush，三种场景三种命运，是进程编程最容易踩的坑：

场景 后果 对策
fork() 后父子都 exit() 拷贝来的缓冲区被刷两次，同一内容打印两遍 子进程用 _exit()
exec() 替换映像 未 flush 的缓冲随旧映像直接消失 exec 前 fflush(stdout)
信号处理函数里 printf 输出可能长期滞留在缓冲区（管道重定向时尤其隐蔽，进程被 kill 时直接丢失） 处理函数里用 write()，或至少 fflush

退出码只有 8 位

exit() / _exit() / main() return 的状态只有低 8 位有效（0~255）：

  • exit(-1) → 父进程 WEXITSTATUS 拿到 255
  • exit(256) → 拿到 0（低 8 位被截断）
  • 约定：0 成功，非 0 失败；进程被信号杀死时没有退出码，用 WIFSIGNALED + WTERMSIG 判断
  • shell 里看上一个命令的退出状态：echo $?
