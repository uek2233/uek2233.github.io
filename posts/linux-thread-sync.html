为什么需要线程同步

共享资源与临界区

线程同步是为了对共享资源的访问进行保护，解决数据一致性的问题。

同一进程内的多个线程共享全部系统资源（见 线程基本概念：代码段、数据段、堆、文件描述符……），这意味着：

  • 只要多个线程会读同一份数据，就不会出问题
  • 只要有一个线程会写这份数据，同时还有别的线程在读或写，就必须同步

所谓共享资源，可以是一块内存（全局变量、堆内存）、一个文件描述符、一个硬件寄存器、一段代码的执行权。多线程里最后一种最容易被忽略——"能不能进这段代码"本身就是一种资源。

访问共享资源的那段代码，就是临界区（Critical Section）。临界区本身并不特殊，它的特殊之处在于：一个线程在临界区里时，别的线程不能同时进来（对于写操作）。

竞态条件（Race Condition）

竞态条件的根源是：C 语言里一条语句，很可能对应多条机器指令，而指令之间随时可能被切走。

以 g_count++ 为例，它会被编译成三步：

  1. 读：把 g_count 从内存读进寄存器
  2. 改：寄存器里加 1
  3. 写：把结果写回内存

两次 +1 最后只加了 1，这就是丢更新（lost update）。这类"谁先谁后不定，结果就不定"的现象，就叫竞态条件。

一个真实的坑（实测踩到）：g_count 不加 volatile 时，改成 Release（-O2）编译后连跑三次全部等于 2000000，"竞态消失了"。原因不是没有竞态，而是数据竞争在 C/C++ 里属于未定义行为，编译器有权假定"没有别的线程会动这个变量"，于是把 g_count 整个循环都缓存进寄存器，最后才写回一次内存。这提醒我们两件事：

  1. 不要靠"跑一遍看着没问题"来判断有没有竞态——优化等级、机器负载、核数一变，结果就变；
  2. 真正要修不是加 volatile（它只保证"每次都真的读写内存"，不保证原子性），而是加锁或改用 std::atomic。

记忆法：互斥是"不许一起进"，同步是"排队按次序"，可见性是"写了要算数"。生产者-消费者模型里三件事同时需要：缓冲区的读写要互斥、生产要在消费之前、生产出来的数据消费者要看得见。

互斥锁（Mutex）

互斥锁是线程同步最基础、最通用的手段。

工作原理：在访问共享资源之前对互斥锁进行加锁，在访问完成后释放锁（解锁）。对互斥锁加锁之后，任何其它试图再次对互斥锁进行加锁的线程都会被阻塞，直到当前线程释放互斥锁。如果释放互斥锁时有一个以上的线程阻塞，那么这些阻塞的线程会被唤醒，它们都会尝试对互斥锁进行加锁，当有一个线程成功对互斥锁上锁之后，其它线程就不能再次上锁了，只能再次陷入阻塞，等待下一次解锁。

互斥锁使用 pthread_mutex_t 数据类型表示。

作用:: 对互斥锁加锁。如果锁已经被其它线程持有，则阻塞等待，直到拿到锁为止。

用法：

参数：

  • mutex：指向要加锁的互斥锁

返回值：成功返回 0；失败返回错误码（EINVAL 锁未初始化；EDEADLK 已持有该锁再次加锁，仅 ERRORCHECK 型会返回）

  • pthread 系列函数用返回值判断成败，不看 errno（详见 线程基本概念）
  • 加锁后的代码就是临界区，临界区应尽量短：只包住真正需要保护的那几行数据操作，不要包住 printf、文件 IO、网络请求这类慢操作，否则等于把并发退化成串行

pthread_mutex_unlock() — 解锁

作用:: 释放互斥锁。如果有其它线程正阻塞在这把锁上，其中一个会被唤醒并拿到锁。

用法：

参数：

  • mutex：指向要解锁的互斥锁

返回值：成功返回 0；失败返回错误码（EPERM 当前线程并未持有该锁，仅 ERRORCHECK 型会返回）

注意事项：

  • 谁加锁谁解锁：互斥锁有"属主"概念，不允许 A 线程加锁、B 线程解锁
  • 对未加锁的锁调用 unlock() 是错误（ERRORCHECK 型返回 EPERM，其它类型行为未定义）
  • 不能销毁还没有解锁的互斥锁
  • 到底哪个线程会拿到锁，是不确定的：POSIX 不保证 FIFO，"解锁后刚被唤醒的线程"和"刚跑过来加锁的新线程"谁先拿到锁都有可能，所以不要依赖唤醒顺序来写逻辑（这也是下面"条件变量必须用 while"的根本原因之一）

pthread_mutex_trylock() — 尝试加锁

作用:: 以不阻塞的方式尝试加锁：成功就锁上并立即返回，锁已被占用就立刻返回错误码，不进睡眠。

用法：

参数：

  • mutex：指向要尝试加锁的互斥锁

返回值：成功返回 0；锁已被占用返回 EBUSY（16）

注意事项：

  • 如果线程不希望被阻塞，就使用 pthread_mutex_trylock()：调用后如果互斥锁处于未锁住状态，那么将会锁住互斥锁并立马返回；如果互斥锁已经被其它线程锁住，加锁失败，但不会阻塞，而是返回错误码 EBUSY
  • 典型用途有两个：
    1. 打破死锁：先 lock() 第一把锁，再用 trylock() 去拿其余的锁，失败就释放已持有的锁、稍后重试（见"互斥锁死锁"）
    2. "有就用、没有就跳过"：比如日志线程想试试能不能拿到输出锁，拿不到就攒着待会儿再打，不拖着业务线程
  • trylock() 成功时一样要记得解锁
  • 注意"尝试"不等于"无代价"：拿不到锁却反复循环 trylock，本质上是自己手写的自旋锁，会白烧 CPU（要重试请加退避 usleep）
  • 参考示例：Thread-Sync/src/deadlock.cc（场景 3 就是 trylock 退避破解死锁）

破解办法一：统一加锁顺序（首选）

给所有的锁规定一个全局顺序（比如按"锁的地址大小"或"业务层级"排：先锁账户再锁订单），所有线程都按这个顺序加锁，AB-BA 根本无法构成。

破解办法二：trylock 退避重试

程序设计实在无法按照相同的顺序对一组互斥锁进行锁定，那么就必须采用另外的方法。譬如使用 pthread_mutex_trylock() 以不阻塞的方式尝试对互斥锁进行加锁：线程先使用 pthread_mutex_lock() 锁定第一个互斥锁，然后使用 pthread_mutex_trylock() 来锁定其余的互斥锁。如果任一 trylock() 调用失败（返回 EBUSY），那么该线程释放所有互斥锁，可以经过一段时间之后从头再试。

要点是"拿不到就全放开"——如果失败时还攥着 m1 不放，退避重试只会把死锁换成活锁。

实测里的一个细节：为了让场景 3 的 EBUSY 真的出现，示例里先让 B 线程起来占住 m2，再启动 A 线程——否则 A 手速太快，第一次 trylock 就成功了，反而看不到"退避"的过程。调试并发问题时特意构造时序（加 usleep、调换线程启动顺序）是常用手段。

四种互斥锁类型

互斥锁的类型属性控制着互斥锁的锁定特性，一共有 4 种类型：

类型 同一线程重复加锁 解锁别人的锁 / 解锁未锁定的锁 说明
PTHREAD_MUTEX_NORMAL 死锁 未定义行为 标准互斥锁类型，不做任何错误检查或死锁检测
PTHREAD_MUTEX_ERRORCHECK 返回错误 返回错误 提供错误检查，适合开发期自查
PTHREAD_MUTEX_RECURSIVE 允许（维护加锁次数） 返回错误 递归互斥锁，解锁次数必须等于加锁次数
PTHREAD_MUTEX_DEFAULT Linux 上与 NORMAL 相同 未定义行为 默认行为；PTHREAD_MUTEX_INITIALIZER 和 attr=NULL 创建的都是它

各类的细节：

  • PTHREAD_MUTEX_NORMAL：一种标准的互斥锁类型，不做任何的错误检查或死锁检测。如果线程试图对已经由自己锁定的互斥锁再次进行加锁，则发生死锁
  • PTHREAD_MUTEX_ERRORCHECK：此类互斥锁会提供错误检查。譬如这三种情况都会导致返回错误：
    • 线程试图对已经由自己锁定的互斥锁再次进行加锁（同一线程对同一互斥锁加锁两次）→ 返回 EDEADLK
    • 线程对由其它线程锁定的互斥锁进行解锁 → 返回 EPERM
    • 线程对处于未锁定状态的互斥锁进行解锁 → 返回 EPERM
  • PTHREAD_MUTEX_RECURSIVE：此类互斥锁允许同一线程在互斥锁解锁之前对该互斥锁进行多次加锁，然后维护互斥锁加锁的次数，把这种互斥锁称为递归互斥锁；但是如果解锁次数不等于加锁次数，则是不会释放锁的
  • PTHREAD_MUTEX_DEFAULT：此类互斥锁提供默认的行为和特性。使用宏 PTHREAD_MUTEX_INITIALIZER 初始化的互斥锁，或者调用参数 attr 为 NULL 的 pthread_mutex_init() 函数所创建的互斥锁，都属于此类型

条件变量（Condition Variable）

条件变量用于自动阻塞线程，直到某个特定事件发生或某个条件满足为止。

条件变量通常搭配互斥锁一起使用，是因为条件的检测是在互斥锁的保护下进行的，也就是说条件本身是由互斥锁保护的，线程在改变条件状态之前必须首先锁住互斥锁，不然就可能引发线程不安全的问题。

一句话理解条件变量：互斥锁解决"同一时刻只能我一个人动数据"，条件变量解决"数据还没就绪的时候，我该怎么体面地等着"。

没有条件变量时，想等一个条件往往只能"加锁 → 看条件 → 不满足就解锁 → sleep 一会儿 → 再来一次"，这叫轮询（polling）：要么睡太久反应慢，要么睡太短白烧 CPU，还很难睡对时间。条件变量把这件事交给内核：不满足就睡，谁改了条件谁负责叫醒我。

通知和等待条件变量

条件变量的主要操作便是发送信号（signal）和等待。发送信号操作即是通知一个或多个处于等待状态的线程，某个共享变量的状态已经改变，这些处于等待状态的线程收到通知之后便会被唤醒，唤醒之后再检查条件是否满足。等待操作是指在收到一个通知前一直处于阻塞状态。

pthread_cond_signal() 和 pthread_cond_broadcast() 均可向指定的条件变量发送信号，通知一个或多个处于等待状态的线程。

两者区别：

  • pthread_cond_signal() 函数至少能唤醒一个线程
  • pthread_cond_broadcast() 函数则能唤醒所有线程
  • 使用 pthread_cond_broadcast() 函数总能产生正确的结果（唤醒所有等待状态的线程），但函数 pthread_cond_signal() 会更为高效，因为它只需确保至少唤醒一个线程即可

该用哪个？ 判断标准很简单：

场景 选择 理由
唤醒后所有等待者都能干活（如"数据已就绪，谁抢到算谁的"） signal() 一次只叫一个，避免"惊群"
等待者的条件各不相同，或"状态变了大家都得重新判断" broadcast() 叫错人等于没人干，会卡住
不确定 / 图省心 / 调试期 broadcast() 总是正确，只是略低效

实测演示（./pthread_cond broadcast）：三个线程都卡在同一个条件变量上，主线程先把条件置真、signal() 一次 → 只醒来 1 个；随后 broadcast() → 剩下 2 个全醒。

条件变量的判断条件，为什么必须用 while 而不是 if

使用条件变量，都会有与之相关的判断条件，通常情况下会涉及到一个或多个共享变量。使用了 while 循环、而不是 if 语句，来控制对 pthread_cond_wait() 的调用。

  • 当线程从 pthread_cond_wait() 返回时，并不能确定判断条件的状态，应该立即重新检查判断条件，如果条件不满足，那就继续休眠等待

从 pthread_cond_wait() 返回后，并不能确定判断条件是真还是假，其理由如下：

  • 当有多于一个线程在等待条件变量时，任何线程都有可能会率先醒来获取互斥锁，率先醒来获取到互斥锁的线程可能会对共享变量进行修改，进而改变判断条件的状态
  • 可能会发出虚假的通知（spurious wakeup）

读写锁（Read-Write Lock）

读写锁是互斥锁的特化：如果把"读"和"写"区别对待，共享数据的读操作可以并行，只有写操作才需要独占，那么"读多写少"的场景能获得比互斥锁更好的并发度。

读写锁有 3 种状态：读模式下的加锁状态（以下简称读加锁状态）、写模式下的加锁状态（以下简称写加锁状态）和不加锁状态。

  • 一次只有一个线程可以占有写模式的读写锁，但是可以有多个线程同时占有读模式的读写锁。因此可知，读写锁比互斥锁具有更高的并行性
  • 当读写锁处于写加锁状态时，在这个锁被解锁之前，所有试图对这个锁进行加锁操作（不管是以读模式加锁还是以写模式加锁）的线程都会被阻塞
  • 当读写锁处于读加锁状态时，所有试图以读模式对它进行加锁的线程都可以加锁成功；但是任何以写模式对它进行加锁的线程都会被阻塞，直到所有持有读模式锁的线程释放它们的锁为止

读写锁非常适合于对共享数据读的次数远大于写的次数的情况。

  • PTHREAD_PROCESS_PRIVATE：私有读写锁。只有本进程内的线程才能够使用该读写锁

读写锁的两个坑（重点）

坑一：读锁不能"升级"为写锁

"先 rdlock 读一下，发现要改，就地 wrlock 升级"——这是必然死锁的写法。因为 wrlock 会等"所有读者释放读锁"，而自己就是那个还没放手的读者。

正确做法是先解锁读锁，再重新加写锁，然后重新检查条件（因为中间状态可能已经被别人改了）：

坑二：读者优先会导致"写饥饿"

glibc 默认的读写锁策略是读者优先（PTHREAD_RWLOCK_PREFER_READER_NP）：只要还有读者在读，新来的读者可以插队拿到读锁，写线程就得一直等。如果读请求持续不断，写线程可能长时间拿不到锁（写饥饿）。

  • 想缓解，可以在属性里设成写者优先：pthread_rwlockattr_setkind_np(&attr, PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP)（带 _np 说明是非标准扩展，只在 glibc 上用）
  • 注意 PTHREAD_RWLOCK_PREFER_WRITER_NP 这个"看起来最像"的取值在 glibc 上有历史 bug，实际效果和"读者优先"一样，要用带 NONRECURSIVE 的那个
  • 实用建议：读写锁适合"读远多于写、且读操作很短"的场景。如果你的写操作很重，或者读写比例并不悬殊，老老实实用互斥锁反而更简单可靠——别为了"看起来更高级"而用读写锁

自旋锁（Spin Lock）

自旋锁与互斥锁相似，但是互斥锁在无法获取到锁时会让线程陷入阻塞等待状态；而自旋锁在无法获取到锁时，将会在原地"自旋"等待（反复检查锁的状态，即忙等 / busy-wait，线程始终占着 CPU，不进睡眠）。

试图对同一自旋锁加锁两次必然会导致死锁，而试图对同一互斥锁加锁两次不一定会导致死锁，原因在于互斥锁有不同的类型（RECURSIVE 型允许重复加锁）。

自旋锁通常用于以下情况：需要保护的代码段执行时间很短，这样就会使得持有锁的线程会很快释放锁，而"自旋"等待的线程也只需等待很短的时间；在这种情况下就比较适合使用自旋锁，效率高！

自旋锁与互斥锁的区别

对比项 互斥锁 自旋锁
拿不到锁时 线程睡眠（让出 CPU，进内核调度） 原地自旋（不睡，反复重试，占着 CPU）
实现方式 基于自旋锁（futex）实现，所以自旋锁相较于互斥锁更加底层 更底层
开销 锁开销要远高于自旋锁；自旋锁的效率远高于互斥锁 更轻量
适用临界区长度 长临界区（睡眠的代价可以被摊平） 极短的临界区
单核上的表现 正常 自旋浪费整个时间片（单核上通常不该用）
中断服务函数中 不能用（中断里不能休眠、不能被抢占） 可以用
是否可递归 RECURSIVE 型可以 不可以，第二次加锁必然死锁

关于"中断服务函数里用自旋锁"：在执行中断服务函数时要求不能休眠、不能 被抢占（内核中使用自旋锁会自动禁止抢占），一旦休眠意味着执行中断服务函数时主动交出了 CPU 使用权，休眠结束时无法返回到中断服务函数中，这样就会导致死锁！

这也是为什么在实际项目中，内核/驱动里到处是自旋锁，而用户态应用几乎只用互斥锁：用户态临界区一旦变长，自旋等待的那个线程就是在毫无意义地烧 CPU（还会因为它"占着 CPU 不睡"，把持锁线程挤下线，让情况更糟）。只有在"我赌它几十纳秒内就放锁"时，自旋才划算。

自旋锁初始化

自旋锁使用 pthread_spinlock_t 数据类型表示。当定义自旋锁后，需要使用 pthread_spin_init() 函数对其进行初始化；当不再使用自旋锁时，调用 pthread_spin_destroy() 函数将其销毁。

参数：

  • lock：指向要初始化 / 销毁的自旋锁
  • pshared：表示自旋锁的进程共享属性
    • PTHREAD_PROCESS_SHARED：共享自旋锁。该自旋锁可以在多个进程中的线程之间共享
    • PTHREAD_PROCESS_PRIVATE：私有自旋锁。只有本进程内的线程才能够使用该自旋锁

返回值：成功返回 0；失败返回错误码（EBUSY 锁未解锁就销毁）

注意事项：

  • 自旋锁必须初始化，且初始化开销不小，绝不要在临界区里反复 init/destroy（那就完全违背了它的设计初衷）
  • 与互斥锁不同，pthread_spinlock_t 没有静态初始化宏，只能靠 pthread_spin_init()——所以它不能像 PTHREAD_MUTEX_INITIALIZER 那样直接给全局变量用

自旋锁加锁和解锁

pthread_spin_lock() 函数或 pthread_spin_trylock() 函数对自旋锁进行加锁，前者在未获取到锁时一直"自旋"；对于后者，如果未能获取到锁，就立刻返回错误，错误码为 EBUSY。使用 pthread_spin_unlock() 函数对自旋锁进行解锁。

参数：

  • lock：指向要操作的自旋锁

返回值：成功返回 0；失败返回错误码（trylock 拿不到锁返回 EBUSY）

注意事项：

  • 临界区里不要做任何可能阻塞的事（printf、文件 IO、malloc、调用别人写的函数）——自旋锁的设计前提就是"临界区极短"

信号量（Semaphore）

信号量是是计数型的同步工具：不仅能当互斥锁用，还能表达"还剩几个资源可用"这种语义，是互斥锁 + 条件变量做不到的。

信号量分两种：

  • 无名信号量（sem_t + sem_init()）：放在内存里，线程间或（配合共享内存）进程间使用
  • 有名信号量（sem_open()）：有 /名字，存在于文件系统中（/dev/shm/sem.名字），天生可以跨进程使用

用法：

参数：

  • sem：指向要操作的信号量
  • sval（getvalue）：输出参数，回填当前计数

返回值：成功返回 0；失败返回 -1 并设置 errno（trywait 计数为 0 时返回 EAGAIN，wait 被信号中断返回 EINTR）

注意事项：

  • P/V 操作本身是原子的，不需要再加锁保护信号量自己
  • sem_post() 可以在信号处理函数里安全调用（POSIX 明确它是异步信号安全的），这是它相对条件变量的一个优势——"中断/信号里通知，主流程里 sem_wait 等"是常见模式

  1. 先问"这是不是只有一个变量的加减/标志位" → 是就用 std::atomic，别上锁
  2. 再问"要不要等条件" → 要就用「互斥锁 + 条件变量」，或信号量

实战：生产者-消费者模型

生产者-消费者是线程同步的"Hello World"，把前面所有工具串起来了：一个线程往缓冲区放数据，其它线程从缓冲区取数据，需要同时满足：

  1. 缓冲区的读写要互斥（不能一边放一边取同一格）
  2. 缓冲区满时生产者必须等，空时消费者必须等（同步）
  3. 生产者放入的数据，消费者要能看到（可见性，由锁/信号量保证）

两个实践要点

要点一：通知发在解锁前还是解锁后？

示例里统一是"先 signal 再 unlock"。原因：在不持锁时发通知，被唤醒的线程可能立刻抢占互斥锁却发现条件又不成立，于是白白多睡一轮（俗称"唤醒风暴"）；而持锁发通知虽然会让被唤醒者再等一下，但正确性不受影响。POSIX 允许两种顺序，先通知后解锁是更常见的推荐写法。

要点二：signal 还是 broadcast？

在上面这个"有界缓冲区"里，生产者只关心"有没有空位"，消费者只关心"有没有数据"，两份条件互不干扰，所以用 signal() 各叫一个最划算。但只要出现"等待者的条件不一样"（比如同时有"等队列非空"和"等队列为空"两类线程挂在同一个条件变量上），就必须用 broadcast()——否则 signal() 叫醒的可能是一个条件根本不成立的线程，而真正该干活的那个还在睡。

判断口诀：通知方不知道谁该醒，就用 broadcast()。 图省心用 broadcast() 永远不会错，只是效率略低。

Helgrind / DRD（valgrind） valgrind --tool=helgrind ./app 数据竞争、锁顺序问题、死锁风险（比 TSan 慢很多）
std::atomic 的 TSan 注解 — 自己写的无锁代码 TSan 会误报，需要 ANNOTATE_HAPPENS_BEFORE 之类标注
-fsanitize=address 与多线程无关但常一起用 越界、释放后使用（多线程里"数据被别的线程释放了"很常见）

实测提醒：本笔记的 race_condition.cc 在 Release（-O2） 下不加 volatile 时竞态会"消失"（编译器把变量缓存进了寄存器）。这类问题 TSan 能抓到，肉眼看代码/跑测试抓不到——所以并发代码"能编译、能跑出对的数"完全不能证明它是对的。

函数 所属章节 一句话作用
PTHREAD_MUTEX_INITIALIZER 互斥锁 静态初始化互斥锁（等价于默认属性）

PTHREAD_COND_INITIALIZER 条件变量 静态初始化条件变量

pthread_cond_wait() 条件变量 原子解锁 + 睡眠，被唤醒后重新加锁
pthread_cond_timedwait() 条件变量 限时等待，超时返回 ETIMEDOUT
pthread_cond_signal() 条件变量 至少唤醒一个等待线程

PTHREAD_RWLOCK_INITIALIZER 读写锁 静态初始化读写锁
pthread_rwlock_init() / pthread_rwlock_destroy() 读写锁 动态初始化 / 销毁读写锁
pthread_rwlock_rdlock() 读写锁 读模式加锁（共享，可多个读者）
pthread_rwlock_wrlock() 读写锁 写模式加锁（独占）
pthread_rwlock_tryrdlock() / trywrlock() 读写锁 不阻塞的读 / 写尝试加锁，失败返回 EBUSY
pthread_rwlock_timedrdlock() / timedwrlock() 读写锁 限时版读 / 写加锁
pthread_rwlock_unlock() 读写锁 解锁（读锁写锁共用这一个函数）
pthread_rwlockattr_init() / destroy() 读写锁属性 初始化 / 销毁读写锁属性对象
pthread_rwlockattr_setpshared() / getpshared() 读写锁属性 设置 / 获取进程共享属性
pthread_rwlockattr_setkind_np() 读写锁属性 设读者/写者优先（glibc 扩展，_NP）
pthread_spin_init() / pthread_spin_destroy() 自旋锁 初始化 / 销毁自旋锁（须指定 pshared）
pthread_spin_lock() 自旋锁 加锁，拿不到就在原地自旋
pthread_spin_trylock() 自旋锁 尝试加锁，失败立即返回 EBUSY
pthread_spin_unlock() 自旋锁 解锁
sem_init() / sem_destroy() 信号量 初始化 / 销毁无名信号量（初值决定语义）
sem_wait() 信号量 P 操作：计数 -1，为 0 则阻塞
sem_trywait() 信号量 P 操作非阻塞版（不能减返回 EAGAIN）
sem_timedwait() 信号量 P 操作限时版（超时返回 ETIMEDOUT）
sem_post() 信号量 V 操作：计数 +1 并唤醒等待者（信号安全）
sem_getvalue() 信号量 读取当前计数（仅供观测，不可当判断条件）
sem_open() / sem_close() / sem_unlink() 信号量 有名信号量：创建打开 / 关闭 / 删除（可跨进程）
std::atomic<T> 补充 单变量无锁原子操作（见 C++ 原子变量基础总结）
