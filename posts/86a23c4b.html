一个规范的 CMake 工程通常长这样：

关键设计原则

层级 职责 谁维护
.tool 声明编译环境（编译器路径、架构、flags） 每个开发者/CI 各有一份
build.sh 读取 .tool → 调用 cmake → 构建 项目维护者（一次写好）
CMakeLists.txt 描述构建目标、依赖、编译选项 项目维护者
toolchain.cmake 定义交叉编译链变量 平台移植时编写

2. .tool 文件 — 编译配置中心

.tool 是项目的 编译环境声明文件，采用 key=value 格式（类似 .env），规定了本次编译使用什么编译器、目标架构、编译模式等。

2.2 常用字段说明

字段 含义 必填
TOOLCHAIN_PREFIX 交叉编译工具链前缀（如 arm-linux-gnueabihf-） 交叉编译时必填
TOOLCHAIN_PATH 工具链安装根目录 交叉编译时必填
SYSROOT_PATH 目标系统的 sysroot（头文件+库） 交叉编译时推荐
BUILD_TYPE 编译模式，对应当前构建 推荐
BUILD_DIR cmake 构建目录（与 source dir 分离） 推荐
C_FLAGS / CXX_FLAGS 额外编译标志 可选
LDFLAGS 链接器额外标志 可选
EXTRA_CMAKE_ARGS 传给 cmake 的额外 -D 参数 可选
JOBS make -j 并行数 可选（默认取 CPU 核心数）
INSTALL_PREFIX make install 安装路径 可选

💡 为什么不把这堆东西直接写死在 CMakeLists.txt 里？

因为 .tool 是环境相关的——不同开发者的工具链路径可能不同，CI 和本地的 BUILD_TYPE 也可能不同。CMakeLists.txt 应该保持平台无关，把环境差异抽到 .tool 里。

6. toolchain.cmake — 交叉编译链

当 .tool 中设置了 TOOLCHAIN_PREFIX，build.sh 会加载 cmake/toolchain.cmake。

⚠️ toolchain.cmake 的重要规则：

  1. 它必须在第一个 project() 调用前生效——通过 cmake -DCMAKE_TOOLCHAIN_FILE=... 传入
  2. 里面只能用缓存变量（set(... CACHE ...)）或者环境变量（$ENV{...}），不能用普通的 CMake 变量（因为在 project() 之前普通变量还不稳定）
  3. 编译器路径必须用绝对路径，否则 CMake 可能在 PATH 里找到宿主机编译器

8. 常见问题与技巧

8.1 CMake 常用变量速查

变量 含义
CMAKE_SOURCE_DIR 顶层源码目录（最顶层 CMakeLists.txt 所在目录）
CMAKE_BINARY_DIR 构建目录（cmake -B 指定的目录）
CMAKE_CURRENT_SOURCE_DIR 当前处理的 CMakeLists.txt 所在目录
CMAKE_CURRENT_BINARY_DIR 当前 CMakeLists.txt 对应的构建目录
PROJECT_SOURCE_DIR 最近一次 project() 命令的源码目录
PROJECT_BINARY_DIR 最近一次 project() 命令的构建目录
PROJECT_NAME project() 定义的项目名
PROJECT_VERSION project() 定义的版本号

8.3 build.sh 的 set -euo pipefail 是什么意思？

选项 作用
set -e 任何命令返回非零退出码立即终止脚本（避免错误蔓延）
set -u 使用未定义变量时报错（而不是静默使用空值）
set -o pipefail 管道中任一命令失败，整个管道的退出码就是那个失败命令的退出码

最后的话：这套体系的核心思路是 把编译配置从 CMakeLists.txt 中抽离到 .tool 和 toolchain.cmake，让 CMakeLists.txt 保持"纯逻辑"——描述构建目标和依赖关系，而不是具体某台机器的工具链路径。这样项目可以轻松地在不同环境（开发机、CI、交叉编译）之间移植，每个人只需修改自己的 .tool 文件即可。
