信号（Signal）

本文是 Linux 应用编程学习笔记，配套示例代码位于宿主机： /data/build/ubuntu-22.04-gcc/root/linux/Siganl/src/（下文以 Siganl/src/xxx.cc 简写引用）

基本概念

信号是事件发生时对进程的通知机制，也可以把它称为软件中断。信号与硬件中断的相似之处在于能够打断程序当前执行的正常流程，它其实是在软件层次上对中断机制的一种模拟。大多数情况下，无法预测信号到达的准确时间，所以信号提供了一种处理异步事件的方法。

每个信号都有一个编号和一个名字（宏定义），如 SIGINT（编号 2）、SIGKILL（编号 9）。

信号的发生

  1. 硬件发生异常：硬件检测到错误条件并通知内核，随即再由内核发送相应的信号给相关进程。如除数为 0、数组访问越界导致引用了无法访问的内存区域等
  2. 终端按键：在终端上按下 Ctrl + C 产生中断信号 SIGINT，终止前台运行的进程；按下 Ctrl + Z 产生暂停信号 SIGTSTP，暂停当前前台运行的进程（注意：暂停是 SIGTSTP，不是 SIGCONT，SIGCONT 是"继续运行"）
  3. kill() 系统调用：将任意信号发送给另一个进程或进程组
  4. kill 命令：shell 下将信号发送给其它进程
  5. 软件事件：检测到某种软件条件已经发生——进程所设置的定时器已经超时、进程执行的 CPU 时间超限、进程的某个子进程退出等等

💡 终端信号（Ctrl+C/Ctrl+Z）只会发送给前台进程组。如果程序在后台运行（如 ./prog &），终端按键产生的 SIGINT 不会送达后台进程——这就是"中断符时系统并不会给后台进程发送 SIGINT 信号"这句话的含义。此时只能通过 kill 命令主动发送。

信号的处理方式

进程收到信号后，有三种处理方式：

  1. 忽略信号：进程不去理会它、直接忽略。但有两种信号决不能被忽略——SIGKILL 和 SIGSTOP，它们不能被忽略的原因是：它们向内核和超级用户提供了使进程终止或停止的可靠方法（即使捕获也不行，只能执行默认操作）
  2. 捕获信号：执行用户自定义的处理函数
  3. 执行系统默认操作：每种信号都有各自的默认动作（终止进程 / 生成 core / 忽略 / 停止 / 继续）

信号是异步的

进程无法预测该事件产生的准确时间，进程不能够通过简单地测试一个变量或使用系统调用来判断是否产生了一个信号。因此信号处理函数可能在任何时刻被调用，这也引出了"可重入函数"问题（见文末补充）。

信号的完整生命周期（补充）

一个信号从产生到处理，会经历几个阶段：

  • 产生（Generation）：事件发生，内核为该进程生成一个信号
  • 未决（Pending）：信号已产生但尚未递送给进程。如果信号被阻塞（在信号掩码中），信号就会停留在未决状态
  • 递送（Delivery）：信号送达进程，触发处理动作
  • 处理（Handling）：执行默认操作 / 忽略 / 调用处理函数

理解这个流程对后面学习 sigprocmask()、sigpending()、sigsuspend() 至关重要。

信号的分类

可靠信号与不可靠信号

Linux 信号机制基本上是从 UNIX 系统中继承过来的。早期 UNIX 系统中的信号机制比较简单和原始，进程可能对信号做出错误的反应，以及信号可能丢失。

在 Linux 系统下，信号值小于 SIGRTMIN（34）的信号都是不可靠信号（即标准信号）：

  • 不排队：同一个信号在阻塞期间多次产生，只会递送一次
  • 早期 SysV 的 signal() 处理完信号后动作会被重置为默认（现已改进）

实时信号与非实时信号

  • 非实时信号（标准信号）：都不支持排队，都是不可靠信号
  • 实时信号：都支持排队，都是可靠信号

一般将非实时信号（不可靠信号）称为标准信号，编号 1~31；实时信号编号 34~64（SIGRTMIN ~ SIGRTMAX）。

特性 标准信号（1~31） 实时信号（34~64）
排队 不排队，多次产生只递送一次 排队，多次发送多次递送
伴随数据 无 可携带一个 int 或指针（sigqueue）
传递顺序 无保障 编号越小优先级越高，先递送；同号按发送顺序
应用自定义 仅 SIGUSR1/SIGUSR2 两个 31 个信号均可自定义用途

signal() — 设置信号处理函数（简单方式）

作用:: 为指定信号安装处理函数（捕获或忽略），是设置信号处理方式最简单的方式。

用法：

参数：

  • signum：要设置的信号编号
  • handler：取值 SIG_DFL（执行默认操作）、SIG_IGN（忽略该信号），或自定义处理函数指针 void handler(int sig)

返回值：成功返回此信号之前的处理函数指针；失败返回 SIG_ERR，并设置 errno

注意事项：

  • 当一个应用程序刚启动的时候（或者程序中没有调用 signal() 函数），进程对所有信号的处理方式都设置为系统默认操作
  • 当一个进程调用 fork() 创建子进程时，子进程会继承父进程的信号处理方式——因为子进程在开始时复制了父进程的内存映像，所以信号捕获函数的地址在子进程中依然有意义（exec 之后则会被重置为默认）
  • 用 signal() 安装的处理函数，执行期间该信号本身会被自动阻塞（相当于没设 SA_NODEFER），防止递归打断
  • 可移植性差：不同 UNIX 实现语义不同（SysV 上处理完会重置为 SIG_DFL，BSD 上不会）。Linux glibc 的 signal() 遵循 BSD 语义（内部用带 SA_RESTART 的 sigaction() 实现）。跨平台代码请使用 sigaction()

kill() — 向进程或进程组发送信号

作用:: 将信号发送给另一个进程或进程组，是"发信号"最核心的接口（kill 命令底层就是它）。

用法：

参数：

  • pid：
    • pid > 0：发送给指定 PID 的进程
    • pid == 0：发送给调用进程同进程组的所有进程
    • pid == -1：发送给所有有权限发送的进程（除 init 和内核线程）
    • pid < -1：发送给进程组 -pid 的所有进程
  • sig：要发送的信号；sig == 0 时不发送任何信号，只做错误检查（可用于探测进程是否存在、是否有权限）

返回值：成功返回 0；失败返回 -1，并设置 errno（ESRCH 进程不存在、EPERM 无权限、EINVAL 信号无效）

注意事项：

  • 发送权限：进程向另一个进程发送信号是需要权限的，并不是可以随便给任何一个进程发送。超级用户 root 可以将信号发送给任何进程；对于非超级用户（普通用户），基本规则是：发送者进程的实际用户 ID 或有效用户 ID，必须等于接收者进程的实际用户 ID 或有效用户 ID
  • 经典探测用法：kill(pid, 0) 返回 0 表示进程存在且有权访问；返回 -1 且 errno 为 ESRCH 表示进程不存在

alarm() — 定时发送 SIGALRM

作用:: 在指定秒数后向当前进程发送 SIGALRM 信号的系统调用，常用于实现超时控制。

用法：

参数：

  • seconds：定时秒数

返回值：返回之前闹钟剩余的秒数；如果之前没有设置过闹钟，返回 0

主要功能：

  • 定时发送信号：seconds 秒过去后，内核向该进程发送 SIGALRM 信号
  • 默认行为：SIGALRM 的默认操作是终止调用它的进程（所以要使用它必须提前捕获）

  • 精度是秒级，需要更高精度用 setitimer() / timer_create() / POSIX timer
  • 参考示例：Siganl/src/alarm.cc（命令行 ./alarm -t 3 指定倒计时，处理函数里再次 alarm(countdown_time) 实现循环倒计时）

信号掩码与阻塞

内核为每一个进程维护了一个信号掩码（其实就是一个信号集），即一组信号。当进程接收到一个属于信号掩码中定义的信号时，该信号将会被阻塞、无法传递给进程进行处理，内核会将其挂起；直到该信号从信号掩码中移除，内核才会把该信号递送给进程从而得到处理。

阻塞期间到达的信号进入未决（pending）状态，可用 sigpending() 查询。

  • 当应用程序调用 signal() 或 sigaction() 为某一个信号设置处理方式时，进程会自动将该信号添加到信号掩码中——这样保证了在处理一个给定的信号时，如果此信号再次发生，它将会被阻塞（即处理函数执行期间不会被打断）
  • 使用 sigaction() 设置处理方式时，可以额外指定一组信号（sa_mask），当调用信号处理函数时将该组信号自动添加到信号掩码中，处理函数结束返回后再移除
  • 使用 sigprocmask() 系统调用，随时可以显式地向信号掩码中添加/移除信号

⚠️ 注意：SIGKILL 和 SIGSTOP 不能被阻塞（内核直接忽略对它们的屏蔽请求）。

实时信号

实时信号（SIGRTMIN ~ SIGRTMAX，编号 34~64）较之于标准信号，优势如下：

  1. 信号范围扩大：31 个实时信号均可用于应用程序自定义目的；而标准信号仅提供了两个可用于自定义：SIGUSR1 和 SIGUSR2
  2. 队列化管理：内核对于实时信号采取队列化管理。将某一实时信号多次发送给另一个进程，将会多次传递此信号；相反，对于某一标准信号正在等待某一进程，此时即使再次向该进程发送此信号，信号也只会传递一次
  3. 伴随数据：发送实时信号时，可为信号指定伴随数据（一个整形数据或者指针值），供接收进程在它的信号处理函数中获取
  4. 传递顺序有保障：多个不同的实时信号处于等待状态时，率先传递编号最小的信号（编号越小优先级越高）；同一类型的多个信号排队时，传递顺序与发送顺序保持一致

实时信号使用要点：

  • 发送进程使用 sigqueue() 系统调用向另一个进程发送实时信号以及伴随数据
  • 接收进程要为该信号建立信号处理函数：使用 sigaction() 并加入 SA_SIGINFO 标志，这样处理函数才能接收到实时信号以及伴随数据

补充：信号编程实战要点

可重入函数（异步信号安全）

信号处理函数可能在主程序任意位置被插入执行，因此处理函数中只能调用异步信号安全（async-signal-safe）函数，否则可能破坏主程序正在维护的数据结构（如 malloc 的空闲链表、printf 的缓冲区），导致数据错乱甚至死锁。

  • ✅ 安全：write、read、open、close、waitpid、kill、sigaction、sigprocmask、_exit、sleep 等（完整列表见 man 7 signal）
  • ❌ 不安全：printf/cout、malloc/free、strcpy、sprintf、exit、abort 等
  • 处理函数里想打印信息，用 write(STDOUT_FILENO, buf, len) 而非 printf

volatile sig_atomic_t

信号处理函数与主程序之间共享的标志变量应声明为 volatile sig_atomic_t：

  • sig_atomic_t 保证读写是原子的（int 大小），volatile 防止编译器优化掉对标志的检查
  • 信号处理函数的原则：只置标志/记录，不在处理函数里做重活（如释放内存、加锁——处理函数里使用非可重入锁可能死锁）

SIGCHLD 与僵尸进程

子进程终止时，父进程会收到 SIGCHLD。如果父进程不处理，子进程会变成僵尸进程（Zombie），占用内核进程表项。

  • 在 sigaction() 中注册 child_handler，父进程即可自动回收子进程
  • 或者使用 SA_NOCLDWAIT 标志：子进程退出时内核自动回收，不产生僵尸
  • 常见坑：waitpid 返回 -1 且 errno 为 ECHILD 表示没有子进程可回收，循环要能正确处理

信号与线程

  • 信号发送给进程时，由该进程中任意一个未阻塞该信号的线程处理，具体哪个线程不确定
  • 每个线程有自己的信号掩码：多线程程序用 pthread_sigmask() 代替 sigprocmask()；常用模式是主线程启动前阻塞所有信号，再由专职线程统一处理
  • pthread_kill(thread, sig) 可以向指定线程发送信号
  • 信号处理函数执行在哪个线程上下文中是不确定的，处理函数里要避免使用线程局部以外的共享状态

core dump 调试

  • 生成 core 的条件：ulimit -c unlimited（默认通常是 0，不生成）
  • core 文件位置由 /proc/sys/kernel/core_pattern 决定
  • 用 gdb 分析：gdb ./prog core，输入 bt（backtrace）查看崩溃调用栈——是排查段错误、断言失败（abort）的利器
